# Experiment H: does an OKF guide add value beyond an API contract?

> **Terms.** A *guide* is a generated OKF bundle: a folder of markdown files, one per module or package. A *contract* is the dependency's OpenAPI document. This page was written **before any run of H1, H2 or H3** and fixes what will be measured and how it will be judged. Changes after the first data are listed at the end under *Deviations*.

## The question

Tests A to G showed that a guide of an unreadable dependency makes cross-repo work possible. They did not ask whether a cheaper, ordinary artefact would have done as well. Most services already have, or can generate, an API contract. So: **for an agent that cannot read a dependency, what does a generated guide add beyond (a) a contract and (b) a short hand-written reference?**

## Five ways of giving the agent knowledge of the dependency

| Arm | The agent gets |
| --- | --- |
| `none` | A line saying the dependency exists elsewhere. |
| `contract` | The dependency's OpenAPI document. For the Java backend it is generated from the source with `scripts/make_h_openapi.py` (route, parameter names and where they travel, request and response schemas with inherited fields, the framework's summary and notes text); for the Python service it is the one FastAPI generates itself. |
| `notes` | A short hand-written reference (3 KB for the backend, 1 KB for the service; the plan allowed up to 30 KB). Every fact in it was checked against the source. |
| `okf` | The generated guide (`kgen okf`, `recommended` preset). Same guide as tests D to G. |
| `source` | The dependency's source, readable. The upper bound. |

Honest limits of the arms: the backend contract is derived from the source by our script, not emitted by a running Spring application (there is no JDK on the test machine); the hand-written reference was written by the experimenter who also knew the tasks, so it favours `notes`. Both biases make the case for OKF harder, not easier.

## Three parts

| Part | Dependency | Task type | Cells |
| --- | --- | --- | --- |
| **H1** | Renamed Shopizer backend (the one from tests D to G) | The four change tasks of test G: field names, a line identifier, an inheritance chain. Hidden Node tests. | 4 tasks × 5 arms × 4 repetitions = 80 runs |
| **H2** | The same backend | Six questions about which method handles a request and which class it then calls. A contract does not hold call structure. Regex-graded. | 6 × 5 × 4 = 120 |
| **H3** | A small FastAPI service built for this experiment (`fixtures/pricing-service`, runs in process) | Four changes to a client: paginate, retry on a rate limit, map errors, reproduce the price rules. Hidden Python tests run against the real service. | 4 × 5 × 4 = 80 |

H1 and H2 are static or edit tasks on a real, large codebase. H3 is the only part where behaviour is tested against a running service. In H3 the contract and the guide are both weak on purpose in the places a real contract is: the service does not declare its 404, 409 or the 200 returned on a replayed idempotency key, and the price rules are plain code that no contract holds.

## Network

Network access is **on** for every run of every arm (`sandbox_workspace_write.network_access=true`), unlike tests A to G where the agent's commands had none. Commands that use the network are counted per arm by `scripts/net_check.py`, and results are reported with and without those runs. The backend's identifiers are renamed, so the public Shopizer source would not match by name; this is a mitigation, not a guarantee.

## Measures

1. **Correct**: hidden test passes (H1, H3) or all expected terms are present (H2).
2. **Tokens per run** as a cost proxy, relative to the `none` arm.
3. **Wandering**: runs that read outside their workspace (`scripts/leak_check.py`) and runs that used the network.

## What I expect, fixed in advance

- H1: `contract`, `notes`, `okf` and `source` all pass at nearly the same rate. The contract carries the field names that G needed. `none` stays low.
- H2: `okf` and `source` beat `contract` and `notes`, because call structure is what a contract leaves out. This is the part where I expect OKF to add something.
- H3: `source` wins the behavioural tasks (3 and 4); `contract` and `okf` are level; `notes` does well on the tasks its text covers. OKF adds nothing for a Python service where the contract is generated by the framework.
- Overall: a guide is worth having when the question is *how the dependency works inside*, and not when it is *what its interface is*.

## How it will be judged

- Compare two arms on a task type with Fisher's exact test on pass counts. Fewer than 20 runs per arm cannot separate differences smaller than about 30 points, so **only p < 0.05 is called a difference**; everything else is "no reliable difference".
- Cost is reported as the ratio of means with the spread of the runs. A cost difference smaller than 15% is not called.
- A result that contradicts the expectations above is reported as such.
- Results are reported per part, never pooled across parts; H1/H2 (real, large) and H3 (small, runnable) differ in kind.

## Not tested

Other models; frameworks that emit richer contracts than our script; a contract and a guide together; a guide that is out of date (tests B and D2 cover that); more than four tasks per part.
