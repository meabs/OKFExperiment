Giving coding agents the right knowledge

An architectural recommendation, based on about 1,550 controlled runs of a coding agent
OKF Experiment · October 2026

1. Summary

Coding agents have to understand code before they can change it. When the code is in front of them, they can search it. When a change depends on another team's service, a private library or any code the agent cannot read, the agent has to be given the facts, or it will guess. This paper recommends how to supply those facts.

The principle. Coding agents do not necessarily need more documentation. They need the right information, at the right time, from a source that can be trusted. Where the source of a dependency is out of reach, give the agent an authoritative, versioned contract first. Add structural knowledge only for tasks the contract cannot support. Check, before the agent uses it, that what you supplied matches the version of the dependency in use.

We tested this with one agent on a real Java backend and web storefront. We compared giving the agent nothing, an API contract, a three-kilobyte hand-written note, a generated "guide" of the backend, and the backend's real source. The guide is a folder of markdown files produced from the code by a script, in a format called OKF (Open Knowledge Format). It lists classes, routes and calls, with the file and line each fact came from.

Five results matter for architecture:

  1. If the agent can already read the code, extra generated knowledge did not make it more accurate. It cost more tokens, and when it was out of date it misled the agent.
  2. If the agent cannot read a dependency, supplying facts about it made a very large difference: changes passed in about 3 of 20 runs with nothing and in 18 or 19 of 20 with a guide.
  3. For changes that depend on an interface (names, paths, fields), a contract or a short note did about as well as the guide, and cost less.
  4. For questions about what calls what inside the dependency, only the guide or the source worked. That shows the guide helps agents answer structural questions. It does not show that it helps them make better changes. A later test in a large repository the agent could read found no gain in the quality of its changes from a guide (section 4.5).
  5. Out-of-date knowledge produced confident, wrong answers, and nothing placed inside the knowledge itself protected the agent.

2. The problem

Most real changes cross a boundary. A storefront team calls a backend owned by someone else. A service uses a vendored library. A migration touches a system whose source is held in another repository, or is not available to the agent at all. In each case the agent has two options: to be told the facts, or to guess.

Guessing is not harmless. In our tests, agents given nothing guessed the names of request fields from habit and mostly got them wrong. They also spent a great deal of effort searching and then gave up, using about 785,000 tokens per question on average and answering correctly in 1 of 24 cases.

Architects therefore need an answer to a practical question: what is the cheapest dependable way to give an agent knowledge of code it cannot read? Generated knowledge bases are one answer. API contracts and short reference notes are others. Until now there was little controlled evidence about how they compare.

3. What we tested

We ran about 1,550 runs of one agent (OpenAI's Codex, model gpt-5.6-luna, medium reasoning). Each run was one question or one change, started from scratch, and graded by a hidden test or an exact answer check. We recorded correctness and tokens used, which is a stand-in for cost and time. We called a difference real only when a standard statistical test (Fisher's exact test) gave p below 0.05.

4. What we found

4.1 Where the agent can read the code, a guide adds cost, not accuracy

On a small library, agents answered 14 or 15 of 15 questions and made 8 or 9 of 9 changes correctly, with or without a guide. The recommended guide cost 1.30 times the tokens in one run and 1.07 in a rerun (the second not clearly different). Copying in a guide for a library the agent could read cost 1.25 times the tokens, with all 72 changes passing either way.

4.2 Where it cannot, facts decide the outcome

Cross-repository changes passed in 3 of 20 runs with nothing. With a guide they passed in 19 of 20 (small tasks) and 18 of 20 (harder tasks). In the harder tasks, an agent with the backend's real source also passed 18 of 20. The three passes with nothing were on tasks whose answer can be guessed.

This is a clear result, but it is a result about answering questions. It does not show that a better answer produces a better change. The network was on in this experiment, and 56 of 120 runs cloned the public repository; all 8 contract passes were among them. A separate part (H3, a small running service) was contaminated because agents without the source found it on the disk, so we draw no conclusions from it except one: a contract that listed only one success code led agents to treat the service's other success code as an error.

4.5 In a large repository the agent can read, a guide did not improve the change

Experiment I asked whether structural knowledge improves an engineering outcome, not only an answer. In the 1,173-file backend, with the source readable, the agent had to rename a method and update every caller. The names were common (findOne, saveOrUpdate, toLocale), so a plain text search finds three to ten times more hits than there are real callers. A script graded each result exactly: every true call site renamed and nothing else changed. Agents were also kept from reading anything outside their workspace.

The pass rates did not differ reliably (p = 0.78), and the guide cost about 22% more tokens, which was reliably more. Failures were mostly missed calls, or edits to callers of a different class with the same method name, and they happened in both arms. The guide's own call information was incomplete in three places; the agents mostly did not follow it into error. This is one repository, one kind of task and one model. It does not say that structural knowledge cannot help a change, only that on this task it did not.

4.6 Out-of-date knowledge is the main hazard

We renamed four things in the backend after the guide was made. Four questions had new answers.

None of the 46 wrong answers hedged. When the agent could read the code, one sentence in its instructions, "read the source to confirm before you rely on it", cut repeated old facts from 8 of 12 to 0 of 12. When it could not, nothing placed inside the guide helped: not warnings, not expiry dates, not confidence labels. Labels say how a fact was found, not whether it is still true. With an instruction to disclose guesses, agents did say they were relying on a guess in 6 of 8 wrong answers, but accuracy did not improve.

5. Recommendations

Findings are measured. Recommendations are our judgement, built on them. Where a recommendation goes beyond what we measured, it says so.

R1. Do not give agents generated knowledge of code they can already read.

Evidence: experiments A, B, C. No accuracy gain, higher cost, and a stale guide misleads. Instead: rely on the source and existing tools, and add "read the source to confirm before you rely on it" to the agent's instructions.

R2. For a dependency the agent cannot read, supply a versioned API contract first.

Evidence: H1. A contract matched the guide on interface changes at lower cost. Why architects care: most services already have, or can generate, one. It is also the form your teams already review and version. Caution: a contract states the success codes it was written with, and agents trust it. Make sure it is complete, including every success and error response.

R3. Add a short, authoritative reference for the facts a contract cannot carry.

Evidence: H1, where a 3 KB note was the cheapest arm and among the best. Use it for: conventions, the field names people get wrong, error behaviour and business rules. A note written by the dependency's owners costs little and was the most efficient help we measured. This is a measured result with an important bias: we wrote the note knowing the tasks.

R4. Add structural knowledge only where tasks need internal call relationships.

Evidence: H2, where the guide answered 21 of 24 against 8 for a contract. A generated guide is one way to supply it; the source, where it can be shared, is another. Boundary of the evidence: we showed better answers to questions, not better changes. Treat this as a targeted capability for specific tasks, such as impact analysis, not as a default layer.

R5. Put business behaviour and invariants in specifications and tests, not in generated knowledge.

Evidence: a generated guide or contract holds structure, not rules. In H3, rules such as price calculation were found only by agents that read the service. That experiment was contaminated, so this is a recommendation, not a measured result. Behaviour that matters should live where it is verified.

R6. Make freshness a gate, not a hope.

Evidence: B and D2. A stale guide of an unreadable dependency was repeated as fact in 14 to 16 of 16 answers. Warnings, banners, expiry dates and labels did not prevent it. Recommendation: every piece of knowledge supplied to an agent should record the version of the thing it describes. Check that version against the dependency in use before the agent runs, in your pipeline. We built and ran two such checks (a guide matches its code; a copied-in guide matches its dependency's files) on small examples. They have not been run in a real pipeline, so treat them as a starting point.

R7. Use confidence labels only to make guesses visible.

Evidence: E, F, G. Labels did not make agents more accurate. With an instruction, they made agents say when a conclusion rested on a guess. A wrong fact labelled as certain was trusted every time, so label only what the source states.

6. A reference approach

Think of the knowledge supplied to an agent as layers, each added only when the task needs it. The owner of the dependency publishes each layer, versioned with the code it describes.

The agent can read the repositorySource and existing tooling, plus "read the source to confirm"Measured (A, B, C)
It needs another service's APIVersioned API contractMeasured for names and paths (H1)
It needs a few extra factsSmall authoritative referenceMeasured, with a note written knowing the tasks (H1)
It needs internal call relationshipsTargeted structural knowledge, possibly a generated guideMeasured for questions only (H2)
It needs business behaviour or invariantsAuthoritative specifications and testsRecommendation
Generated knowledge may be staleValidate against the dependency version before useHarm measured (B, D2); checks are a recommendation

Operating it

  • Ownership. The dependency's owner publishes the contract, the reference and, if used, the guide. Consumers copy a pinned version and do not write their own.
  • Pinning and checks. A copy records the version it came from. A pipeline step compares it with the dependency in use and fails on a mismatch.
  • Instructions. A short file tells the agent where the layers are, and tells it to read the source to confirm wherever it can.
  • Measure before you scale. Try your own agent on a handful of real tasks, with and without each layer, before investing in more.

7. What this does not justify

  • It does not justify an enterprise-wide knowledge platform. The experiments compared ways of giving an agent facts about one dependency, not a programme of knowledge management.
  • It does not show a guide is needed everywhere, nor that it improves software changes beyond a contract.
  • It does not show that equal pass rates mean equal quality. Our samples were small.

8. How far to trust this

  • One agent and one setting. Other models may behave differently.
  • Few tasks. Experiments A to G had 3 to 5 runs per question per condition; H had 16 to 24 per arm. Small differences are not reliable.
  • We wrote the tests. The questions, hidden tests, planted changes and the note were ours. The contract was generated by our script.
  • Contamination. H2 had network access and H3 let agents find material on the disk. We report H2 with and without the affected runs and draw no conclusion from H3.
  • The code was altered. The backend had names changed and changes applied as uncompiled text edits.
  • Mistakes we made and kept. Early runs of A and B told the agent to verify in every condition, which hid differences, so we reran them. The first H3 run is archived and unreported. Experiment I's first graded batch was discarded for a grader defect and rerun; both are published.

9. What to do next

  1. Test a contract and a guide together. We did not, and it is the combination this paper recommends.
  2. Test changes that need internal structure. Show that structural knowledge improves the change, not only the answer.
  3. Repeat on another model and on real drift from real commits.
  4. Run the freshness checks in a real pipeline and measure how often they fire.
